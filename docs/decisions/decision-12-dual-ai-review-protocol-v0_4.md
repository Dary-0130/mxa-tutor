### R1 — 互抓反例 28 / 34(v0.3 扩展)

任一方提方案后,另一方**强制 grep 对方凭印象部分**:

- 白名单 / regex / 关键词清单
- 数据假设(数量 / 比例 / 阈值)
- 时间估算 / 工作量估算
- 跨任务时序假设
- "依据 X 而 X 我未实地核查"类引用
- **(v0.3 新增)精确事实(返回码 / 行号 / commit hash / 索引行存在性 / 目录入仓状态 / 函数签名)— 是否 grep 或 conversation_search 验证过?**

**强制 grep 不是软建议,是工艺纪律**。若一方接受对方判断但未跑过 grep,等同 R3 违反(K_28a 候选记入)。

### R2 — 公开 challenge 清单(沿用 v0.2)

接受对方意见时,产出文档**显式标注**:接受 N 条 / challenge M 条(逐条理由)/ 抓出对方反例 K 条(逐条证据 + 修法)。禁止隐式全盘接受(用"很到位"/"抓得对"/"全部承认"等措辞而无清单)。

### R3 — PM 看到双 AI 分歧(沿用 v0.2)

每轮 R 反馈给 PM 时,产物**必含**:
- 同意部分(说明为何同意)
- 分歧部分(若有;双方理由 + 各自工作量)
- 互抓反例部分(若有)
- 若该轮无实质分歧 → 必须说明 grep 了哪些区域 + 为什么无分歧 / 反例

禁止给 PM 一份"统一方案"让 PM 仅点头。

### R4 — 最终决断在 PM(沿用 v0.2)

强制 challenge,不强制 disagreement。允许真无分歧但必须 grep 报告。禁止双 AI 自己达成完全一致后让 PM 仅 rubberstamp;也禁止为对称硬凑形式化分歧。

### R5.1 — 入仓模式起稿粒度自查(v0.4 新增,K_28b 子类化) ⭐

**目的**:防 K_28b 子类反例(架构师 v0.1 起稿 § 范围 段所有文件入仓动作,未明示入仓模式决策点供 PM 拍板) — 本任 v0.1 起稿粒度漏明示 git mv 覆盖 vs create_file 并存,PM 主动救场触发 v0.1.3 决议补丁。

**强制纪律**:架构师 v0.x 起稿任务卡 § 范围 段所有文件入仓动作时,**必须明示入仓模式决策点**:
- **若 task 对应实体卡 v(x-1) 已在 main 仓库存在** → 必须明示 "v(x-1) → v(x) 走 `git mv` 覆盖" 还是 "v(x-1) 保留 + create v(x) 并存" 两种模式,**等 PM 拍板**,不许凭印象写"任务卡入仓"模糊措辞
- **若新任无前置同名实体卡** → 明示 "create_file 新建" 模式,沿用 task-203 v0.4 / task-305 v0.2 / task-308b 等先例

**默认范本**:
- 沿用决策 12 v0.2 → v0.3 → v0.3.2 → v0.4 入仓 git mv 模式(若实体卡迭代关系,有 git log --follow 历史追溯需求)

**架构师起稿 § 范围 / 修改文件清单 checklist 必含本规则**(详 § 4.4 KPI 自查第 12 条)。

### R6 — Codex 第三方实测层(v0.3 新增) ⭐

**目的**:补 GPT R1/R2 文本审盲区。文本级互审无法覆盖召回 / 排序 / 阈值 / 真实数据分布等"必须跑代码才能验证"的问题。

**触发条件**(任一):
- 任务卡涉及召回 / 排序 / 阈值 / 数据校准 / 性能门槛 / 评测指标
- 架构师设计阶段无法基于真实数据校准(凭推测拍数字)
- GPT R1/R2 challenge 清单出现"无法判断 / 需实测"类条目

**执行方式**:
- 第一棒实施前 Codex 跑预调研(产物 `<task>_prep/<topic>_audit.md`,D 盘 untracked)
- 涉及召回 / 阈值的棒位前 Codex 跑诊断(产物 `<task>_diagnose/<topic>_audit.md`)
- 实测结果回流到任务卡 v0.X+1 修订(K_28b 子类型自抓 / 抓出)

**禁止**:Codex 不跑实测就直接开工召回 / 阈值类生产代码。

**本任实战 ROI**:K_28b #3 教训(Gate top_k=5 凭推测设计 → Codex 跑 gate 4/6 暴露 → 修订到 top_k=10 后 6/6 PASS)— 文本审三轮(架构师 + GPT R1 + GPT R2)都没抓到,只有 Codex 实测抓到。

### R6.1 — Codex 完工 report 实证(v0.3.2 新增) ⭐

**目的**:防 K_36(工程职责边界漏)— Codex 完工时凭记忆 / 凭主观范围声明 report,可能漏列范围外文件改动(如 TASK-305 v0.2 task-403-v0_3.md 范围漂移)。

**强制纪律**:
- Codex 完工 report 必须按 `git diff --stat origin/main` 实证列出**全部改动文件**,不许凭记忆 / 凭 commit 列表 / 凭范围声明
- 若实际改动文件 ≠ 派单范围列出的文件 → **停手报 PM 解释为什么有范围外文件**;不许在 PR body / 完工 report 中省略
- commit 拆分要与文件作用域 1:1 对应(不许一个 commit 改多个不相关文件)

**架构师派单 prompt 必含本规则**(详 § 7.1.2)。

**本任实战 ROI**:TASK-305 v0.2 Codex 完工 report 漏列 task-403-v0_3.md 入仓,K_36 +1 触发独立阈值 ≥ 2 立项;TASK-203 v0.4 派单 prompt 已含 R6.1 → Codex 主动 `git diff --stat` 实证 → 3 文件改动严格匹配派单范围 → K_36 兑现防范。
