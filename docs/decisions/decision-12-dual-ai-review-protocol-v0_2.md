### 1.1 触发场景

| 轮次 | Claude 反应 | 应有反应 |
|---|---|---|
| GPT 第一份 6 硬伤 | 全部承认 | 至少 1-2 条应 challenge |

### 1.2 问题陈述

**单 AI 偏误**(决策 09 反例 28):架构师无 repo 凭推理写;现有兜底 = Codex Stage 0 实测。

**新型偏误**(本协议针对):**双 AI 协同自洽 / 互相认账放大错位**。形态:
- **A. 一方凭印象写 → 另一方默认接受**(本任 Claude 抄 GPT § E 白名单 `dict[str, str]`,未抓 GPT 反例 28)
- **B. 一方提反驳 → 另一方过度认账**(本任 Claude 接受 GPT R1 6 P0 时未 challenge,等于把判断外包)
- **C. 双方达成"统一方案" → PM 只点头**(本任倾向 GPT R1 全过 → 进 Codex,PM 无实质决策点)

**根因**:架构师对 GPT 的判断默认接受,因为"GPT 抓得很到位"是真的;但 GPT 自身也凭印象,**双 AI 自洽不等于双重过滤**,反而可能放大错位。

## 2. 协议 5 条规则

### R1 — 互抓反例 28

任一方提方案后,另一方**强制 grep 对方凭印象部分**:
- 白名单 / regex / 关键词清单
- 数据假设(数量 / 比例 / 阈值)
- 时间估算 / 工作量估算
- 跨任务时序假设
- "依据 X 而 X 我未实地核查"类引用

**强制 grep 不是软建议,是工艺纪律**;若一方接受对方判断而**未跑过 grep**,等同于 R3 违反(详下)。

### R2 — 公开 challenge 清单

接受对方意见时,产出文档**显式标注**:
- 接受 N 条
- challenge / 反驳 M 条(逐条理由)
- 抓出对方反例 28 K 条(逐条证据 + 修法)

**禁止**隐式全盘接受(用"很到位"/"抓得对"/"全部承认"等措辞而无清单)。

### R3 — PM 看到双 AI 分歧

每轮 R 反馈给 PM 时,产物**必含**:
- 同意部分(说明为何同意)
- 分歧部分(若有;双方理由 + 各自工作量)
- 互抓反例部分(若有;双方各自的反例 28 候选)
- **若该轮无实质分歧 / 无反例互抓 → 必须说明 grep 了哪些区域 + 为什么无分歧 / 反例**(v0.2 新增)

**禁止**给 PM 一份"统一方案"让 PM 仅点头。

### R4 — 最终决断在 PM ⭐ **v0.2 修订**

双 AI 互审产物**是输入,不是产出**。
PM 拿到"分歧清单 + 理由清单 + grep 核查报告"做实质决断。

**v0.2 修订核心**(GPT R2 P0-3 + Claude 自抓协议自反):

**原 v0.1 R4 例外段**(删除):
> ❌ "方向性 / schema / 验收 / 时序 / 范围任一,必须保留至少 1 个分歧点供 PM 决断"

**问题**:这条本身是**反例 31 反面同源**(加硬反伤),诱导双 AI **凑分歧而非真分歧** —— 形式化分歧污染 PM 决策点。等于在写一份反"反例 31"协议时,撞了"反例 31 反面同源"。

**v0.2 R4 新规则**:**强制 challenge,不强制 disagreement**

- **强制**:任一方提方案,另一方**必须跑 R1 互抓 grep + R2 公开 challenge 清单**
- **允许**:若 grep 后**确无实质分歧 / 反例**,§ 2 写"无方向性分歧",但必须说明:
  1. **grep 了哪些区域**(白名单 / regex / 数据假设 / 时间估算 / 跨任务时序)
  2. **为什么没有分歧**(grep 找到的对方判断是否有实证依据 / 是否对方已实地核查)
  3. **是否抓到反例 28 / 30 / 31 候选**(若有,记入 K 累计)

**禁止**双 AI 自己达成完全一致后让 PM 仅 rubberstamp;**也禁止**为对称硬凑形式化分歧。

### R5 — 反例 28 抓到要入仓

任一方抓出对方反例 28 / 30 / 31,**记入下轮 docs 补丁 chore**;累积:
- 决策 09 反例 28 累积(沿用),**单 AI 反例 28**(架构师无 repo 单方面)
- **决策 12 反例 33 累积**(双 AI 协同自洽,本协议新增)
- **K_28 / K_30 / K_31 分列**(v0.2 新增,详 § 4.1 升仪条件)

## 3. 工艺执行细节

### 3.1 R 轮文档拆分

每轮 R 反馈产出**2 份文件**(沿用 v0.1):
1. **任务卡正文**(`task-NNN-v0_X.md`):只装方案 + 接口契约 + 验收 + Codex 提示;**不掺 challenge**
2. **challenge 清单**(`task-NNN-v0_X-rN-challenge.md`):装互审产出
   - § 1 同意清单
   - § 2 分歧清单(若有;否则写"无方向性分歧"+ grep 核查报告)
   - § 3 互抓反例 28 / 30 / 31(条目 + 证据 + 修法)
   - § 4 给 PM 的实质决策点
   - § 5 累积统计(K_28 / K_30 / K_31 分列)
   - **§ 6 + 后续 R 轮增补**(v0.2 新增;sibling 文件可累积多轮)

### 3.2 challenge 清单是否入仓?

- **每轮 challenge 清单文件**:作为任务卡同 PR 的 sibling 文件入仓;长期可追溯
- **后续架构师传承**:每个 task 的 challenge 清单**是历史先例**,新任接手时可读

### 3.3 互抓反例 28 / 30 / 31 的判定

一方抓出另一方"反例 28 / 30 / 31 候选"需提供证据:
- 引用对方文档具体位置(line / § / 段)
- 说明"凭印象"的依据(对方未引用源文档 / 未跑 grep / 未实测)
- 提供修法(Codex Stage 0 兜底 / 实测后调整 / 标注"草案待实测")

PM 接到反例候选时:
- 接受 → 入 K_28 / K_30 / K_31 累计
- 拒绝 → 标"非反例,误抓"(也入累积但单独标记,衡量误抓率)

## 6. 反例 31 风险与对冲(v0.2 强化)

**反例 31 反面同源风险**:为流程而流程加硬,反伤效率。

**v0.1 → v0.2 教训**:
- v0.1 R4 例外段 "必须保留至少 1 个分歧点" = **协议自反 bug** = 反例 31 反面同源
- 等于在写一份反"反例 31"协议时,撞了"反例 31 反面同源"
- **Claude 自抓 K_31 = 1**(决策 12 协议自反)

**对冲**(v0.2 已修):
- R4 改"强制 challenge,不强制 disagreement"
- 允许真无分歧;但必须 grep 报告
- challenge 清单**精简**(分歧 ≤ 5 / 反例 ≤ 5 / 决策点 ≤ 3),不写小学作文
- 执行级琐碎细节(commit 编号 / 文件名)允许双 AI 一致
- 若某 task 范围极窄(如 docs 补丁 chore)双 AI 真没分歧 → § 2 明示"本任范围窄,无方向性分歧 + grep 核查报告";**§ 3 互抓反例 28/30/31 仍必跑**
