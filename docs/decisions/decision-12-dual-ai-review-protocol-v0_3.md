## 2. 协议规则(v0.3 修订)

继承 v0.2 R1-R5,新增 R6 / R7。

### R1 — 互抓反例 28 / 34(v0.3 扩展)

任一方提方案后,另一方**强制 grep 对方凭印象部分**:

- 白名单 / regex / 关键词清单
- 数据假设(数量 / 比例 / 阈值)
- 时间估算 / 工作量估算
- 跨任务时序假设
- "依据 X 而 X 我未实地核查"类引用
- **(v0.3 新增)精确事实(返回码 / 行号 / commit hash / 索引行存在性 / 目录入仓状态 / 函数签名)— 是否 grep 或 conversation_search 验证过?**

**强制 grep 不是软建议,是工艺纪律**。若一方接受对方判断但未跑过 grep,等同 R3 违反(K_28a 候选记入)。

### R2 — 公开 challenge 清单(沿用 v0.2)

接受对方意见时,产出文档**显式标注**:接受 N 条 / challenge M 条(逐条理由)/ 抓出对方反例 K 条(逐条证据 + 修法)。禁止隐式全盘接受(用"很到位"/"抓得对"/"全部承认"等措辞而无清单)。

### R3 — PM 看到双 AI 分歧(沿用 v0.2)

每轮 R 反馈给 PM 时,产物**必含**:
- 同意部分(说明为何同意)
- 分歧部分(若有;双方理由 + 各自工作量)
- 互抓反例部分(若有)
- 若该轮无实质分歧 → 必须说明 grep 了哪些区域 + 为什么无分歧 / 反例

禁止给 PM 一份"统一方案"让 PM 仅点头。

### R4 — 最终决断在 PM(沿用 v0.2)

强制 challenge,不强制 disagreement。允许真无分歧但必须 grep 报告。禁止双 AI 自己达成完全一致后让 PM 仅 rubberstamp;也禁止为对称硬凑形式化分歧。

### R5 — 反例抓到要入仓(v0.3 扩展分类)

任一方抓出反例 28a / 28b / 30 / 31 / 34 候选,**记入下轮 docs 补丁 chore**。累积:

- **K_28a**(经典:架构师无 repo 凭推理写)— 沿用
- **K_28b**(v0.3 立子类:架构师起稿粒度问题,含阈值粒度 / 起稿口径转写 / 阈值未基于真实数据)— **新增**
- **K_30**(跨段同步漏)— 沿用
- **K_31**(协议自反 / 反例 31 反面同源)— 沿用
- **K_34**(v0.3 立项:语义记忆错位 / 压缩上下文后引用历史日志当现状)— **新增**
- **守门救场**(Stage 0 严格执行触发的反例拦截)— **单独累积,不计入 K 总**

### R6 — Codex 第三方实测层(v0.3 新增) ⭐

**目的**:补 GPT R1/R2 文本审盲区。文本级互审无法覆盖召回 / 排序 / 阈值 / 真实数据分布等"必须跑代码才能验证"的问题。

**触发条件**(任一):
- 任务卡涉及召回 / 排序 / 阈值 / 数据校准 / 性能门槛 / 评测指标
- 架构师设计阶段无法基于真实数据校准(凭推测拍数字)
- GPT R1/R2 challenge 清单出现"无法判断 / 需实测"类条目

**执行方式**:
- 第一棒实施前 Codex 跑预调研(产物 `<task>_prep/<topic>_audit.md`,D 盘 untracked)
- 涉及召回 / 阈值的棒位前 Codex 跑诊断(产物 `<task>_diagnose/<topic>_audit.md`)
- 实测结果回流到任务卡 v0.X+1 修订(K_28b 子类型自抓 / 抓出)

**禁止**:Codex 不跑实测就直接开工召回 / 阈值类生产代码。

**本任实战 ROI**:K_28b #3 教训(Gate top_k=5 凭推测设计 → Codex 跑 gate 4/6 暴露 → 修订到 top_k=10 后 6/6 PASS)— 文本审三轮(架构师 + GPT R1 + GPT R2)都没抓到,只有 Codex 实测抓到。

### R6.1 — Codex 完工 report 实证(v0.3.2 新增) ⭐

**目的**:防 K_36(工程职责边界漏)— Codex 完工时凭记忆 / 凭主观范围声明 report,可能漏列范围外文件改动(如 TASK-305 v0.2 task-403-v0_3.md 范围漂移)。

**强制纪律**:
- Codex 完工 report 必须按 `git diff --stat origin/main` 实证列出**全部改动文件**,不许凭记忆 / 凭 commit 列表 / 凭范围声明
- 若实际改动文件 ≠ 派单范围列出的文件 → **停手报 PM 解释为什么有范围外文件**;不许在 PR body / 完工 report 中省略
- commit 拆分要与文件作用域 1:1 对应(不许一个 commit 改多个不相关文件)

**架构师派单 prompt 必含本规则**(详 § 7.1.2)。

**本任实战 ROI**:TASK-305 v0.2 Codex 完工 report 漏列 task-403-v0_3.md 入仓,K_36 +1 触发独立阈值 ≥ 2 立项;TASK-203 v0.4 派单 prompt 已含 R6.1 → Codex 主动 `git diff --stat` 实证 → 3 文件改动严格匹配派单范围 → K_36 兑现防范。

### R7 — 精确事实自动校验(v0.3 新增) ⭐

**目的**:K_34 5 次累积全部是"凭语义记忆复述精确事实"导致;派单前强制校验。

**派单前架构师必跑**(强制):

| 事实类型 | 校验命令 |
|---|---|
| 返回码 / 状态码 | `grep <code> docs/06_OUTPUT_CONTRACTS.md` 或 conversation_search 历史契约 |
| 文件 / 目录入仓状态 | `git ls-files <path>` 列 tracked 清单 |
| 索引行存在性 | `grep "<TASK-X>" docs/03_TASK_INDEX.md` |
| 行号 / commit hash | view `<file>` 或 `git log <ref>` 直查 |
| 函数 / 类签名 | `grep -n "^def <name>" <path>` |
| 跨任务时序假设 | conversation_search 上游 task 实际完工状态 |

**派单文档头部声明已校验项清单**(`§ Stage 0 精确事实校验`)。Codex Stage 0 复核;**任一漏跑 → R3 违反(K_34 候选记入)**。

**本任实战 ROI**:K_34 = 5 全部命中点(/upload 200 vs 202 / 任务卡已入仓措辞 / eval/ad_hoc 沿用 / 派单误删 eval/ / 03 索引 TASK-209 行存在性),若 R7 强制执行可全部规避。

**v0.3.2 强化**:**架构师无 repo 时,前任交接 / 历史 docs 描述 ≠ git 实测真值源**;涉及 main 真实状态(文件存在性 / 行号 / commit hash / 目录内容 / 接口签名)时,必须让 PM 实测兜底,不许凭交接文字描述直接派单。本任 v0.4 v0.1.2 派单前 PM 实测 `git ls-tree 5cc00c5 docs/tasks/` 发现前任交接 § 5 "task-403 v0.2.2.1 + v0.3 并存"描述错(实际 5cc00c5 只有 v0.2.2.1),K_28a +1 自抓教训。

### R7.1 — 修订时强制 grep 全文兜底(v0.3.2 新增) ⭐

**目的**:防 K_30(跨段同步漏)— 架构师 R 轮修订时只改"关键段"未做全文同步,造成多处 instance 残留(TASK-305 v0.2 v0.1.1+v0.1.2 / TASK-203 v0.4 v0.1.1 累积教训)。

**强制纪律**:
- 任何 v0.x 任务卡 / 决策类自身升级修订完成后,**架构师必须在交付前用 grep 兜底扫旧字面**:
  - 修订关键字面的所有旧表达(如 `≤ 3000 字` / `MAX_CITATION_RETRIES` / `待 R1 决议` 等)
  - 涉及命名 / 数值 / 状态变更时,grep 旧值确认无残留
  - **区分"指令性残留"(必清)vs "描述性引用"(反例账目段记账,保留)**
- 不许只依赖 R 轮中下游(GPT R1 复审 / Codex Stage 0)抓 K_30 同源 — 架构师自己必须先 grep
- 沿用 TASK-305 v0.2 v0.1.2 末尾 grep 验证模式 + TASK-203 v0.4 v0.1.2 末尾首次自抓案例

**架构师起稿 / 修订 checklist 必含本规则**(详 § 4.4 KPI 自查第 10 条)。

**本任实战 ROI**:TASK-203 v0.4 v0.1.2 修订末尾,架构师用 grep 扫旧字面,抓到 1 处 "MAX_CITATION_MAX_ATTEMPTS" 命中 — 但实测为反例账目段描述性引用(描述 K_30 instance "D1 typo MAX_CITATION_MAX_ATTEMPTS"),正确保留。**R7.1 雏形执行成功区分"指令性残留"vs "描述性引用",工艺生效不需要等待 R 轮中下游抓**。

## 3. 工艺执行细节

### 3.1 R 轮文档拆分(沿用 v0.2)

每轮 R 反馈产出 2 份文件:
1. **任务卡正文**(`task-NNN-v0_X.md`):方案 + 接口契约 + 验收 + Codex 提示;不掺 challenge
2. **challenge 清单**(`task-NNN-v0_X-rN-challenge.md`):互审产出
   - § 1 同意清单
   - § 2 分歧清单(若有;否则"无方向性分歧" + grep 核查报告)
   - § 3 互抓反例 28a / 28b / 30 / 31 / 34(条目 + 证据 + 修法)
   - § 4 给 PM 的实质决策点
   - § 5 累积统计(K_28a / K_28b / K_30 / K_31 / K_34 分列)
   - § 6+ 后续 R 轮增补(sibling 文件累积多轮)

### 3.2 challenge 清单入仓(沿用 v0.2)

每轮 challenge 清单作为任务卡同 PR 的 sibling 文件入仓;长期可追溯。

### 3.3 R6 / R7 产物路径(v0.3 新增)

- **R6 Codex 实测层产物** → D 盘 `<task>_prep/` / `<task>_diagnose/`,**永远不入仓**
- **R7 精确事实校验** → 派单文档头部 `§ Stage 0 精确事实校验` 声明已校验项

### 3.4 互抓反例判定(v0.3 扩展)

新增反例 34 判定标准:
- 引用对方文档具体位置(line / § / 段)

- 提供修法:R7 强制校验 + 任务卡 v0.X+1 修订

### 3.5 R6.1 / R7.1 产物路径(v0.3.2 新增)

- **R6.1 完工 report** → Codex PR 正文中包含 `git diff --stat origin/main` 输出 + 文件清单对照表;PM 复核
- **R7.1 grep 兜底** → 修订交付前架构师在 outputs 区 self-check 步骤,grep 输出可不入仓但产物 final 版必须通过
