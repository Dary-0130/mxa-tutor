# TASK-533(spec 校验失败:记录字段级失败详情)

**定位:纯观测能力,不改行为。** 目标只有一个——spec 生成的 pydantic 校验失败时,把**是哪个字段、哪条校验规则**记进现有失败记录,让失败可归因。

**明确不做**(越界即返工):

- 不改任何校验规则、不放宽任何 max_length / 约束(尤其 abstract,那是 TASK-532 的事);
- 不改任何失败行为(该失败的仍失败、错误码对外不变);
- 不加重试、不加救活、不改 pipeline;
- 不动 schema、不 bump CURRENT_SCHEMA_VERSION、不改对外契约。

**做什么:**

spec 生成路径捕获 pydantic ValidationError 处,把 ValidationError.errors() 里的 **loc(字段路径)+ type(校验码,如 string_too_long / missing / too_long)** 提取出来,记进现有失败记录(sanitized 诊断产物 / telemetry / 日志,按现有落点)。

**严格脱敏(决策 11,红线)**:只记 **字段路径 + 校验码 + 计数**,以及**如属长度类校验,可记实际长度与上限值(纯数字)**。

**禁记**:字段值、摘要正文、论文原文、msg 里可能带的输入片段、input 值、LLM raw / partial output、堆栈、str(exc) / repr(exc) / exc_info / logger.exception。

注意 pydantic 的 errors() 默认可能带 input/ctx 等含值字段——**必须显式剔除,只取 loc 与 type**(以及长度类的纯数字上下文)。

让评测试车道(eval/run_paper_pdf_smoke.py)的 summary 能带上这个字段级失败信息,方便按篇看失败归因。

**验收:**

- 单元测试:构造一个超长 abstract(或其他会触发校验失败)的 spec 输入 → 断言记录里出现 loc=abstract + type=string_too_long;断言记录中**不含**任何字段值/正文/堆栈。
- **不需真机全量复跑 8 篇**;但请对 2410.04316 与 2409.11267 各跑一次(spec 阶段即可),**报出这两篇的失败字段路径 + 校验码 + 计数**——这正是本卡的目的:看清它们到底栽在哪道闸。
- make check 全绿;**schema export diff = 空**(显式列)、**前端 typecheck 绿**(显式列)——本卡预期两者零变化。
