## R1 拍板结论(GPT R1 一审 2026-06-13)

### D1 — Citation retry total attempts(改名 retries → attempts;P1-1 + P1-2 修订)

R1 结论:**通过**。采用 **3 attempts total**(含首次 LLM call + 最多 2 次 retry),作为 **MCS 止血上限**(非"数学达标"):

- **2 attempts 覆盖不足**(单次 67% 失败 → 2 attempts 仍 ~45%);**4-5 attempts 显著超 API 60s timeout / 成本红线**(MAX_CITATION_ATTEMPTS > 5 触发 § 自动升 R2 #4)
- **本任不承诺**"3 attempts 把失败率压到 ≤ 10%"(0.67³ ≈ 30%,数学不达标但 timeout 限制 3 已是上限)
- **本任交付标准**:主失败工程 `DAB_SPS_Control.zip` **3/3 smoke 成功**;真实失败率交后续 TASK-306 评测 + 生产日志统计
- 写死 `DEFAULT_CITATION_MAX_ATTEMPTS = 3`(沿用 TASK-203 timeout / max_tokens 写死模式);**不**走 `AppSettings` 注入(触发 § 自动升 R2 #3)
- 命名严守 **attempts 口径**(`citation_max_attempts` / `_citation_max_attempts`)避免 off-by-one 混淆

### D2 — Retry 触发 step 范围

R1 结论:**通过**。`_parse_and_validate` Step 1-5 抛出的 `OverviewGenerationError` 都 retry(JSON parse / Pydantic / file_path / block 四元组 / block_id / line_range)。**不按 step 细分**(细分需扩 `_parse_and_validate` 异常结构 → 超微补丁范围 → 触发 § 自动升 R2 #3)。

### D3 — Retry 日志策略(决策 11 隐私硬约束)

R1 结论:**通过**。
- **失败 attempt 打 INFO**:`project_id` / `attempt`(1-3) / `MAX`(3) / `error_type`(类名,**不打 str(exc) / response.text / failed_step**)
- **重试成功打 INFO**:`project_id` / `attempt=M/3`(P2-2 修订统一格式)
- **首次成功不打额外日志**(避免噪音)
- **最后 FAIL 不重复打**(异常向上抛,handler 已打 ERROR)
- `error_type` 字段名保留 simple(GPT R1 P2-3 给"或保持现状" option,选保持简洁)

### D4 — LLM seed / temperature(P2-1 措辞降级)

R1 结论:**通过,措辞降级**。**本任不改 `DeepSeekTextProvider.chat`**,不传 seed,不传 temperature。retry 的收益来自 **上游 LLM 非完全确定性这一经验假设**(非"DeepSeek 默认 temperature > 0"事实断言)。若 Stage 0 或 PM 实测发现连续 attempts 返回完全相同文本 → 本任仍不改 provider,记录为 **Phase 2 seed/temperature task**(非本任范围)。若 provider 签名需改 → 触发 § 自动升 R2 #2。

```python
# NEW: 私有 helper(本任唯一新增方法;包 retry loop)
async def _generate_overview_with_citation_retry(
    self,
    project_id: str,
    messages: list[LLMMessage],
    project: Project,
) -> ProjectOverview:
    """Citation retry loop。供应商层 _call_with_retry 已处理 LLMTimeoutError /
    LLMServerError 等网络层错;本 helper 只处理 _parse_and_validate 抛出的
    OverviewGenerationError(JSON / Pydantic / citation 校验任一 FAIL)。

    Retry 策略:不指数退避(非网络问题,prompt 相同;retry 收益来自上游 LLM
    非完全确定性这一经验假设;本任不依赖 DeepSeek 默认 temperature 契约,
    Phase 2 候选 seed/temperature 策略)。

    成功才 cache put(由 caller 做);本 helper 不动 cache。
    """
    last_error_type: str | None = None

    for attempt in range(1, self._citation_max_attempts + 1):
        # LLM call(供应商层 _call_with_retry 已处理网络层 retry)
        response = await asyncio.to_thread(
            self.text_provider.chat,
            messages,
            json_mode=True,
            max_tokens=self.max_tokens,
            timeout=self.timeout,
        )
        try:
            overview = self._parse_and_validate(response, project)
        except OverviewGenerationError as exc:
            last_error_type = type(exc).__name__  # "OverviewGenerationError"
            logger.info(
                "Overview citation validation failed: "
                "project_id={} attempt={}/{} error_type={}",
                project_id,
                attempt,
                self._citation_max_attempts,
                last_error_type,
            )
            if attempt >= self._citation_max_attempts:
                raise  # 最后一次 FAIL,向上抛(handler 翻译 502)
            continue  # 否则继续 loop(不 sleep,非网络问题)

        # PASS
        if attempt > 1:
            logger.info(
                "Overview citation retry succeeded: project_id={} attempt={}/{}",
                project_id,
                attempt,
                self._citation_max_attempts,  # P2-2:统一打 attempt=M/N 格式
            )
        return overview

    # 不应到达此处(loop 内必 return 或 raise);防御性兜底
    raise OverviewGenerationError(
        f"Citation retry exhausted: {last_error_type}"
    )
```

### 7.2 异常 / 日志契约(决策 11 兑现)

- **失败日志**:每次 FAIL 打 INFO(metadata-only 4 字段:project_id / attempt / max / error_type;**不打** str(exc) / response.text / failed_step 细节)
- **成功日志**:仅当 attempt > 1 时打 INFO(retry 成功记录;首次成功不打),统一 `attempt=M/N` 格式(P2-2 修订)
- **异常向上抛**:最后一次 FAIL 直接 raise(handler 翻译为 502 OverviewGenerationError)
- **不动既有日志**:`Overview LLM call: ... prompt_version=v0.2-rc` 仍由供应商层打(本任 retry loop 每次 LLM call 都会触发,自然累积)
- **不动 TASK-303 chunking 路径日志**(`build_embed_store_overview_chunk` 内部已有日志)

## 风险与注意点

### R1:Retry 仍失败(LLM 在 3 attempts 内都输出幻觉 citation)
若主验收 `DAB_SPS_Control.zip` 不能连续 3 次新 upload 生成 overview(3/3 smoke 失败),本任验收 FAIL,停手分析日志并报 PM。真实失败率是否 ≤ 10% 不由 3 次 smoke 证明,交后续 TASK-306 / 生产日志统计。Phase 2 候选:seed / temperature 策略、prompt 加强 citation 约束、或更完整的 citation repair。

### R2:Retry 期间 API timeout(R5 同源,Stage 0 #9 兜底)
单次 LLM call ~28s(前任日志);3 attempts 最坏 ~84s,**接近 / 超过 API 层 60s timeout**(uvicorn / nginx / Vite proxy / 前端 fetch)。**Stage 0 #9 必须 preflight 实测中间层 timeout 配置**(GPT R1 P1-3 修订),若 ≤ 60s → 升 R2 停手报 PM,在 [降 attempts / background generation / 延长 timeout] 拍板。

### R3:Cache 污染(本任避免)
**重要**:成功才 cache put(沿用 TASK-203 v0.3 现有行为);retry 期间任何 FAIL 都不 cache put;最后一次 FAIL 抛 502 → 用户刷新触发新 LLM call(cache miss 仍是 miss)。**不引入 negative cache**(若 cache 失败响应 → 用户永远卡住)。

### R4:LLM 成本翻倍 / 三倍(成本红线)
单次 LLM call ~5722 tokens × 3 retry = 17K tokens/工程 worst case;DeepSeek 价格预估每千 tokens ¥0.x → 单工程 ¥几角到几元 worst case。Phase 2 评测时若发现 retry 平均 2.5 次 → 成本可控;若平均 > 2.8 次 → 考虑 seed 策略 / prompt 加强 citation 约束。

### R5:供应商层 retry 与本任 retry 串联(放大 worst case)
供应商层 `_call_with_retry` 3 次 × 本任 citation retry 3 次 = 最坏 9 次 LLM call。但供应商层 retry 触发的是网络/限流错(LLMTimeoutError 等),不会进入本任 citation retry;两层正交。最坏实际是供应商层 3 次 timeout + 本任 1 次 citation FAIL + 供应商层 3 次 timeout + 本任 2 次 citation FAIL + 供应商层 3 次 timeout = 9 次,但 PM 等不到这个时机(api timeout 60s 早就触发)。此类 worst case 由 Stage 0 #9 timeout preflight 与 § 自动升 R2 #8 处理;Codex 不得在实施期自行扩大为 background generation / timeout policy / provider retry 改造。

### R6:Logger 日志噪音(若实测高失败率)
若产品上线后 retry 频繁触发,后端日志会被 `Overview citation validation failed` INFO 充斥。Phase 2 候选:加 metrics 监控失败率,日志改 DEBUG。本任不做。

### R7:overview_service.py 行数膨胀(04 § 4 单文件 ≤ 300 行约束)
TASK-203 v0.3 已经 ~280 行(行数预估,Stage 0 #3 实测确认);本任加 ~30-50 行 → 可能超 300 行。若超 → 抽 `_citation_retry_loop` 私有方法,或拆 `_overview_constants.py`(已建议 § 范围 #2)。**Codex 实施时报告改后行数**;若超 300 → 触发 § 自动升 R2 #5。

### R8:测试 mock 复杂度(D5 同源)
Retry-aware mock 需要让 `fake_text_provider.chat` 按调用次数返回不同响应(第 1 次 FAIL response / 第 2 次 PASS response)。沿用 TASK-203 v0.3 已有的 mock 模式扩展,**不引入新 mock 库**。
