## 2. 真实痛点(决定一切优先级)

### 问题陈述

国内电气、自动化、控制、通信等专业大量使用 MATLAB/Simulink 完成课程作业、毕业设计、论文仿真,但:

- **没有任何一门课系统教过 MATLAB 本身**
- 学生从大三开始被迫用 MATLAB,**全靠自己摸索 + 模仿教材代码**
- 拿到师兄 / 导师 / 教材的工程,**能跑但不懂为什么**
- 写论文要描述自己用的模型,**讲不清楚**
- 老师让在已有工程上改某个参数,**不敢动其他部分**

### 用户的典型句式

听到这些句式 = 我们的产品在帮他:

- "这段代码到底在干什么?"
- "这个 Simulink 模型每个 block 是干嘛的?"
- "我跑出来了但不懂是怎么跑通的"
- "师兄给我的工程我不敢改,怕改坏"
- "写论文我不知道怎么描述这个模型"
- "答辩老师如果问我细节我答不上来"

### 目标用户

**主要用户**:
- 大三 / 大四本科生(电气、自动化、通信、控制专业)
- 研究生(研一研二做仿真实验,研三写论文)

**用户分层**(v3.0 三类并存,决策 22 § 1.3):
- **A 类**:本科生,看不懂教材 / 老师发的 demo / 课程作业(MCS 工程入口服务)
- **B 类**:研究生,看不懂师兄 / 导师 / GitHub / 论文附件的工程(MCS 工程入口服务)
- **C 类(v3.0 新增,paper-to-model 主线)**:论文 / 报告复现用户 — 有论文 / 报告但不知道怎么搭 Simulink 复现路线(C1 v0.1 服务;研究型深度复现 C2 留 v0.2+)

### paper-to-model 真实痛点(v3.0 新增)

C 类用户的痛点 = MCS 痛点的下一步:不只是"看懂手上的工程",而是"手上只有论文 / 报告,要自己搭出能复现的模型"。

**C 类典型句式**(听到这些 = paper-to-model 在帮他):
- "我有这篇论文 / 报告,但不知道怎么搭出 Simulink 模型来复现"
- "论文里的方程 / 框图和 Simulink block 对不上,不知道该用哪个库"
- "论文给了公式,但参数在图里 / 表里,我不知道怎么对应到模型"
- "我搭出来了但结果不对,不知道该调哪个参数"

**副驾边界**(决策 22 § 1.1):paper-to-model 帮 C 类完成复现的主要认知工作(论文理解 + 搭建路线 + 参数对应 + 调参方向),**精确搭建、跑通、收敛由用户自己在 MATLAB 完成**。不承诺打开即跑的 `.slx` 成品。

### 用户特征
1. 中文母语,英文阅读吃力
2. 熟悉国内主流教材(胡寿松/郑君里/樊昌信/刘和平等)
3. 没有系统的 MATLAB 知识体系,边用边学
4. **付费意愿强但单笔有限**(9.9-49 元是甜点)
5. 频次相对高(一学期内会反复有"看不懂"的时刻)

## 4. 技术核心壁垒(为什么我们能赢)

### 壁垒 1:.slx 文件结构化解析 + 教学理解中间层

`.slx` 文件本质是 ZIP 包,内含 XML,精确描述模型所有结构。**我们解析 XML,通用 ChatGPT 只能看截图**。

但**仅解析 XML 不够**。必须再加一层"教学理解中间层"(`ProjectGraph` + `TeachingUnit`),把解析结果转化成教学化的结构化讲解单元,LLM 基于这一层生成讲解。

**核心原则**:**不要让 LLM"猜工程",要让解析器"还原工程",再让 LLM"讲工程"**。

### 壁垒 2:中文教学语境的 Prompt 工程

通用 LLM 的解释偏"技术文档风",我们的输出对齐**国内电气教材的术语和讲法**,学生看得懂。

输出格式必须固定,详见 `05_EXPLANATION_STYLE_GUIDE.md`。

### 壁垒 3:工程级 RAG + 强制证据引用

不是单文件问答,而是**基于整个工程上下文**回答问题。每个回答必须带 `SourceRef` 证据(文件、行号、block)。**没有证据不许硬答**。

### 壁垒 4:垂直评测集

每个版本都用真实工程做回归测试。**评测集越多,产品越值钱**。

### 壁垒 5:论文-模型结构化对应 + 双源证据(v3.0 paper-to-model)

通用 LLM 看论文只能"读懂大意",无法把论文方程 / 框图精确映射到 Simulink 库元件 + 工程参数。paper-to-model 加一层"论文理解中间层"(`PaperSpec` + `PaperGraph` + `ModelGenerationPlan`),把论文结构化成可追溯的搭建路线;参数证据**双源分离**(`document_extracted` 文档抽取 vs `user_supplied` 用户补充),不把猜测伪装成论文依据。**核心原则同 MCS**:不让 LLM"猜模型",让解析器"还原论文结构",再让 LLM"给搭建路线"。(具体数据结构见 `02_ARCHITECTURE_OVERVIEW.md` / `06_OUTPUT_CONTRACTS.md`,不在宪法冻结字段)

## 5. 角色与协作模型

| 角色 | 职责 |
|------|------|
| **PM(你)** | 总控、合规、商业、销售、用户访谈、Task 传递、最终裁决 |
| **架构师(Claude)** | 产品架构、技术决策、Task 拆分、代码 review、验收 |
| **AI 二审(GPT 等)** | 在关键节点做架构压力测试,挑边界、安全、商业漏洞 |
| **实现者(Codex)** | 按 Task 写代码、写测试、提交 PR |

### 协作流程

```
PM 提出需求 / 反馈
  ↓
Claude 拆 Task,写 Task 文档(明确输入、输出、验收标准)
  ↓
(关键节点)AI 二审复审:架构 / 安全 / 商业漏洞
  ↓
PM 把 Task 文档传给 Codex
  ↓
Codex 写代码 + 测试,提交 PR
  ↓
PM 把 PR diff 和测试结果传给 Claude
  ↓
Claude 对照验收标准 review,通过 / 打回
  ↓
通过 → 合并 → 下一个 Task
打回 → PM 把反馈传给 Codex → 改 → 再 review
```

### 何时找 AI 二审复审(避免流程过慢)

只在以下节点找 AI 二审:

1. 项目宪法 / 架构总览大改
2. 核心 Task(TASK-101 / 102 / 104 / 107 / 205 / 304)
3. 上传安全、计费、数据隐私相关改动
4. Codex PR 出现跨层调用、过度抽象、范围膨胀
5. 准备上线收费前

普通 README、简单路由、UI 文案、小修小补,**不用过二审**,避免流程变慢。

### 关键原则
- **一次只走一个 Task**,不并行
- **单一 Task 单一职责**,不许跨 Task 改代码
- **未通过 review 的代码不许合并到 main 分支**
- **Codex 干完每个 Task 必须更新 TASK_INDEX.md 状态**

PM 把 Task 给 Codex 时,**贴这个模板**:


## 7. 技术架构原则(不可违反)

### 分层
```
web/      (前端)
  ↓
api/      (FastAPI 后端)
  ↓
features/ (业务功能)
  ↓
core/     (纯业务,接口定义、教学理解中间层)
  ↑
adapters/ (外部世界实现)
```

- **依赖单向**:上层依赖下层,下层不知道上层
- **core/ 不允许 import 任何外部库**
- **features/ 只依赖 core 接口,不直接 import adapters**
- **api/ 通过 feature service 调用,不直接调 LLM**

### 教学理解中间层(架构关键)

```
Parser 输出(原始结构数据)
  ↓
ProjectGraph(工程结构理解:节点、边、入口、流向)
  ↓
TeachingUnit(教学讲解单元:可被 LLM 直接使用)
  ↓
LLM(基于 TeachingUnit 生成中文讲解)
```

具体实现位置:
- 数据结构在 `core/domain/`(`project_graph.py` / `teaching_unit.py` / `source_ref.py`)
- 构建逻辑在 `features/overview/` 内部模块(`project_graph_builder.py` / `teaching_unit_builder.py`)
- **暂不新增顶层 `features/understanding/`**,决策见 `docs/decisions/20260601-04-understanding-not-top-level-feature.md`

### 模型路由(已定型)
- **文本 / 代码解读 / 简单问答**:DeepSeek V4-Flash(默认)
- **长上下文(整个工程一次性塞入)**:DeepSeek V4-Pro
- **视觉(Phase 2)**:留接口,具体模型后续选

### 不引入的依赖(MCS 阶段)
- LangChain / LlamaIndex(直接调 API 简单 100 倍)
- MySQL / PostgreSQL(SQLite 够用)
- 消息队列
- Redis
- Milvus / Pinecone(用 SQLite + sentence-transformers 做简单向量检索)
- 微服务框架

## 8. 工程规则(给 Codex 必读)

### 写代码必读

- **每文件 ≤ 300 行**,超过强制拆分
- **每个模块必须有 README.md**
- **所有 LLM 调用必须可 mock**(单元测试不调真实 API)
- **所有 prompt 存在 `core/prompts/*.yaml`**,**不写死在代码里**
- **配置走 pydantic + YAML**,**不用环境变量散落**
- **日志用 loguru**,**不用 print**
- **异常处理**:adapter 层捕获原始异常,翻译成业务异常向上抛
- **API 异步**:FastAPI 接口默认 async,长任务走 BackgroundTasks
- **所有教学讲解输出必须符合 `05_EXPLANATION_STYLE_GUIDE.md`**

### 禁止行为
- ❌ feature 直接 import 具体 adapter 类(必须依赖接口)
- ❌ 临时加 pip 依赖(必须先写进 requirements.txt 并 PR review)
- ❌ 把 API Key 写在代码或前端
- ❌ 日志记录用户上传的内容
- ❌ 跨 Task 修改代码(只能动当前 Task 范围内的文件)
- ❌ 引入本宪法未提及的重型依赖
- ❌ **执行用户上传的任何代码**(`.m` / `.mlx` / `.p` / `.mex` 等)

### 命名规范
- Python 文件:`snake_case`
- Class:`PascalCase`
- 函数 / 变量:`snake_case`
- 接口类以 `Provider / Service / Parser / Repository / Builder` 结尾
- 测试文件:`test_<被测模块>.py`
